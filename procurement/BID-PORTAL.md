# 업체 회신 방식 — HTML과 Excel을 함께, 신원·가격은 비공개

**권장 운영안은 ‘초대받은 담당자의 이메일 인증 + 업체별 비공개 작업공간’입니다.** 계정을 아무나 만들게 하거나 주소만 회사별로 나누는 방식은 권하지 않습니다. 설명은 HTML, 대량 수량·단가 입력은 웹 또는 Excel 중 편한 방법을 허용합니다. 같은 내용을 두 번 입력하게 하지 않습니다.

## 지금과 운영버전의 차이

현재 GitHub Pages는 정적 HTML/CSS/JavaScript를 배포하는 서비스입니다. 여기에 입력 화면을 만들 수는 있지만, 현재 저장소에 인증 서버·비공개 견적 DB·업체별 권한·제출 접수 기능이 생기는 것은 아닙니다. [GitHub 공식 설명](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

이번 `contractor/reply.html`은 **로컬 초안 작성 화면**입니다. A가격·B대안·코멘트를 작성하고 파일로 저장하는 용도이며, 로그인·서버저장·회사 신원확인·실제 제출은 하지 않습니다. 작성한 업체명을 믿고 인증된 업체라고 표시하지 않습니다. 실수로 실제 제출로 오인하지 않도록 화면과 내보낸 문서에 이 상태를 표시합니다.

## 왜 HTML만도, Excel만도 아닌가

| 수단 | 적합한 일 | 단독 사용의 문제 | 권장 역할 |
|---|---|---|---|
| HTML | 도면 근거·사양·사진·변경이력 읽기, 항목별 코멘트 | 정적 페이지에는 중앙 저장·인증이 없음 | 자료의 공통 기준과 웹 회신 화면 |
| Excel | 다수 행 복사·붙여넣기, 적산 및 업체 내부 협업 | 버전·누락·단위·회사별 회신 관리가 어려움 | 공통 ID를 유지한 입력·회신 경로 |
| 인증 포털 | 초대·비공개저장·버전·질의·접수증 | 서버/권한/메일·백업 운영 필요 | 반복 입찰·수정협의를 관리하는 운영형 |

61개 상위항목만으로 철근/창호/관경별 상세 적산이 끝나는 것은 아닙니다. 웹에는 공종 요약·제안/질의를 쓰고, 상세 산출서는 공통 Excel 또는 업체 내역서를 첨부할 수 있도록 설계하는 편이 낫습니다.

## 추천: 개별 초대와 이메일 일회용 코드

건축주가 업체와 허용 담당자 이메일을 등록합니다. 업체 담당자는 초대 링크로 들어와 이메일로 받은 일회용 코드를 입력합니다. 비밀번호를 직접 만들 필요는 없습니다. 직원이 둘이면 각각의 이메일을 같은 업체에 연결하고 실제 작성자를 기록합니다. 이메일 접근 확인은 법인대표의 계약서 서명을 대신하지 않으므로 업체 소속/대표권은 건축주가 별도로 확인합니다. [이메일 OTP 기능](https://supabase.com/docs/guides/auth/auth-email-passwordless)

| 방법 | 판단 |
|---|---|
| `/업체A`, `/업체B`처럼 경로만 다름 | 신원확인이나 비밀보호가 아님. 주소를 알면 접근할 수 있게 만들면 안 됨 |
| 긴 무작위 링크만 있음 | 사용은 쉽지만 링크 소지자가 누구인지 확인 못 함. 전달·유출·폐기 관리 필요 |
| 자유가입 후 회사명 선택 | 타 업체 선택/사칭을 막기 위한 추가 승인이 필요해 이번 규모에는 불필요 |
| 초대 링크 + 허용 이메일 OTP | 권장. 링크는 초대 진입점, 실제 데이터 접근은 인증과 업체 소속 권한으로 결정 |

초대 토큰은 충분한 무작위성·만료·1회 사용·취소를 지원하고 서버에는 해시로 저장합니다. 토큰과 가격을 URL 분석도구·공개 로그·Git 이력에 넣지 않습니다. 로그인 뒤 주소에 초대 비밀이 남지 않게 처리합니다. 화면의 숨김/회사명 파라미터를 권한검사로 대신하지 않습니다. [OWASP 접근권한 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 업체가 보게 될 화면

자료실에서 같은 개정의 PDF·DWG·제안서를 읽고 수신 개정을 확인합니다. A안 표에는 참조 사양이 보존되고 옆에 업체의 수량·단가·모델·범위가 들어갑니다. B안은 원안을 덮어쓰지 않고 변경 내용·근거·해당 범위 A/B 금액·증감·관련 공종을 적습니다. 항목별 질문과 첨부도 가능합니다.

임시저장 → 검토 → 제출 → 접수증 순서입니다. **임시저장과 제출을 구분**하고, 제출 시 서버가 업체·실제 작성자·제출시각·문서개정·첨부 해시를 묶은 변경불가 제출본을 생성합니다. 제출 후 수정은 기존 제출본을 덮어쓰지 않고 새 개정으로 남깁니다. 여러 직원의 동시 편집은 버전 충돌을 감지해 조용히 덮어쓰지 않습니다.

## 건축주 화면과 공통 질의

건축주는 업체별 제출/미제출, 누락항목, 다른 수량·제외사항, A기준 총액과 B추천안을 봅니다. 업체A는 업체B의 가격·메모·파일·인원·초대정보를 볼 수 없습니다. 건축주 내부평가·협상메모도 업체에게 노출하지 않습니다.

질문은 기본 비공개입니다. 다른 업체에게도 필요한 설계/범위 답변만 건축주가 가격·제안자정보를 제거해 공통 추가통보로 발행합니다. 각 업체가 어느 개정을 반영했는지 확인한 후 비교합니다. B제안이 서로 배타적이면 증감액을 합산하지 않습니다.

## 운영형 기술 구성안

인증은 이메일 OTP, 저장은 비공개 PostgreSQL, 첨부는 비공개 객체저장소, 화면은 별도 입찰 도메인으로 분리하는 구성을 제안합니다. 구현 예시로 Supabase Auth/DB/Storage를 사용할 수 있습니다. 특정 업체의 유료요금이나 무료 운영 가능성을 이번에 확정한 것은 아닙니다.

`projects` / `companies` / `memberships` / `invites` / `rfq_revisions` / `bid_drafts` / `bid_lines` / `alternatives` / `questions` / `attachments` / `submissions` / `audit_events`를 분리합니다. 회사 소속과 권한은 서버가 관리하며 브라우저가 보낸 `company_id`만 신뢰하지 않습니다. 모든 공개 API와 DB 행에 프로젝트·회사·역할 권한을 강제합니다. [Supabase 행 단위 접근제어](https://supabase.com/docs/guides/database/postgres/row-level-security)

파일은 비공개 저장과 짧은 만료의 다운로드 권한을 사용합니다. 업로드 크기·실제 파일 형식·악성파일/압축폭탄을 점검하고, Excel의 수식 결과/매크로를 서버에서 무조건 실행하지 않습니다. 견적 금액은 서버에서 검증·재계산합니다. 비밀키나 관리자용 DB 키를 프런트엔드에 넣지 않습니다.

외부 업체용 인증메일에는 실제 SMTP/발신도메인과 수신 테스트가 필요합니다. 기본 시험용 발송 설정을 운영메일로 간주하지 않습니다. [Supabase SMTP 운영 설명](https://supabase.com/docs/guides/auth/auth-smtp)

## 실제 개통 전 통과할 검사

| 시나리오 | 통과 기준 |
|---|---|
| 업체A 사용자가 B의 ID로 조회/수정 | 화면뿐 아니라 API/DB/파일 다운로드 모두 거부 |
| 링크만 전달받은 미초대 이메일 | 가입/인증 여부와 무관하게 입찰자료·가격 접근 거부 |
| 취소·만료된 초대/담당자 | 새 로그인·파일 접근·기존 세션 권한도 정책대로 제한 |
| 제출 완료본 편집 | 원본 불변, 재제출 개정과 접수 기록 보존 |
| 두 직원 동시저장 | 충돌 감지/재검토, 뒤에 저장한 값으로 조용히 유실하지 않음 |
| 공통질의 공개 | 다른업체 가격·첨부·신원·내부메모가 섞이지 않음 |
| CSV/Excel/HTML 입력 | 수식삽입·스크립트·과대금액·변조행ID·오래된개정 방어 |
| 메일 실패·서버오류·백업복원 | 미접수를 접수완료로 표시하지 않으며 기록/파일 복구 가능 |

**현재 실제 업체 계정이나 초대 링크, 인증메일 발송·중앙 견적수집은 개통하지 않았습니다.** 이번 산출물은 제안서 R2, 회신용 Excel, 로컬 웹 입력 화면과 운영 설계입니다. 정적 링크를 회사별로 복제해 놓고 안전한 비공개 입찰 시스템이라고 부르지 않습니다.
